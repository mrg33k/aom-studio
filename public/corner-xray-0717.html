Where it fails

two structural faults

Monolith bridges carry the live system

4,143 lines · 90 functions · 0 classes

The live chat bridge (sse-room-bridge) is one flat procedural file. Six of the top eight files are the bridge/relay layer. Any change is high blast-radius — which is exactly why bridge incidents recur.

No shared library — everything is copy-pasted

10 = the most any module is reused

Across 651 files, the most-imported internal module is used by just 10. There is no library layer, so logic gets duplicated. That is the mechanical cause of "three copies of the same prompt / four renderers drifted apart."

The reuse floor

fan-in · how many files import each shared module

A healthy backend has a few modules imported by dozens of callers. Here the ceiling is 10. Compare that to a single god-file holding 90 functions: the code that should be shared lives inline, copied, in hundreds of scripts.

What this means

plain terms
01

The bridge is one big room

The part that talks to users is a single 4,000-line file. Fixing anything there risks everything there. Splitting it into named, testable pieces is the highest-leverage safety move.

02

Rules live in many copies

Because nothing is shared, the same rule (a prompt, a gate, a format) is pasted in several files. Change one, miss the others, they drift. A shared-logic layer stops the drift at the source.

03

The junk drawer hides coupling

640+ scripts in one flat folder with no boundaries means anything can reach anything. Grouping by domain into folders makes what-touches-what visible — the first step to trusting a change.
