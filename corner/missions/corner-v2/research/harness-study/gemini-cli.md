# Gemini CLI — structural brief

**Repo / source:** https://github.com/google-gemini/gemini-cli at 6a466a7e (0.62.0-nightly.20260915) · **Read on:** 2026-09-17 · **Reader:** Claude (corner:corner-v2 R82)
**One line:** Google's terminal coding agent: `packages/core` is the engine (loop, tools, policy), `packages/cli` the Ink UI; for developers working inside a repo.
**Why it is in the study:** the cleanest split between a tool-free stream loop (`Turn`), a scheduler that owns confirmation, and a policy engine that turns "always allow" into a persisted rule.

Rules for this brief: structure over opinion. Every claim cites a file path (or a docs URL for closed products) and, where it helps, a short excerpt. Say "not found" rather than guess. Six sections, same order in every brief, so PATTERN.md can be built row by row.

## 1. The loop
- `GeminiClient.sendMessageStream` (packages/core/src/core/client.ts:912) → `processTurn` (:614) → `new Turn(chat, prompt_id).run()` (core/turn.ts:270). `Turn.run` streams one model call and yields events; it never executes tools. Function calls are pushed to `pendingToolCalls` and yielded as `ToolCallRequest` (turn.ts:456-511).
- Who closes the loop: the CLI. `useGeminiStream` hands requests to the `Scheduler` (core/src/scheduler/scheduler.ts:195); on completion `handleCompletedTools` (packages/cli/src/ui/hooks/useGeminiStream.ts:1972) flattens `response.responseParts` and calls `submitQuery(..., {isContinuation: true})` (:2189). Model → request → scheduler → function responses → model.
- Budgets: `MAX_TURNS = 100` (client.ts:79) bounds recursion per prompt (`boundedTurns - 1`, :899). `maxSessionTurns` default -1 = unlimited (config/config.ts:1246); exceeding yields `MaxSessionTurns` (client.ts:625-630). `ContextWindowWillOverflow` when estimated request > remaining tokens (:701-707). Compression fires at 50% of the window, keeping the last 30% (context/chatCompressionService.ts:41,47).
- Loop detection (services/loopDetectionService.ts): identical tool-call hash 5× (`TOOL_CALL_LOOP_THRESHOLD`, :29), a 50-char content chunk repeated 10× (:30-31), and an LLM judge after 30 turns every 5-15 turns at 0.9 confidence (:42-65, prompt :574). First hit → `_recoverFromLoop` injects "System: Potential loop detected... take a step back" as a user turn and recurses (client.ts:1270-1298); second hit → `LoopDetected`, halt (:822-826).
- Turn end: `Finished` when a finishReason arrives (turn.ts:387-403). If no tools pending, `checkNextSpeaker` (utils/nextSpeakerChecker.ts:43) asks a utility model (JSON schema) whether `user` or `model` speaks next; `model` → auto-send "Please continue." (client.ts:876-899).
- Empty/thinking-only responses get a nudge appended and a retry (core/geminiChat.ts:247-262, :975-977) up to `getMaxAttempts()`.
- Carry-over: in-memory `GeminiChat` history (curated vs comprehensive, nextSpeakerChecker.ts:53-61); BeforeAgent/AfterAgent hooks can stop, block, or inject `<hook_context>` (client.ts:926-949; hooks/types.ts:43-55).

## 2. Skills and tools
- Tool = `BaseDeclarativeTool` producing a `ToolInvocation` (tools/tools.ts:687, :51): `getDescription()`, `toolLocations()`, `shouldConfirmExecute()`, `execute()`. Every tool has a `Kind` (:1116-1130); `MUTATOR_KINDS` / `READ_ONLY_KINDS` (:1131-1145) drive parallelism and checkpoints. `ToolResult { llmContent, returnDisplay }` (:750-768): one payload for the model, one for the human.
- Registry: `ToolRegistry.allKnownTools` Map (tools/tool-registry.ts:251); `registerTool` overwrites on collision (:287-295); `sortTools` orders built-in → discovered-command → MCP by server (:314-347). `getFunctionDeclarations(modelId)` builds the active schema list, dedupes, and in PLAN mode rewrites write tools' descriptions to "ONLY FOR PLANS" (:663-722). Re-run every turn with the routed model (client.ts:807).
- Discovery: built-ins; a `toolDiscoveryCommand` spawned and parsed (:376-470); MCP via `McpClientManager.maybeDiscoverMcpServer` (tools/mcp-client-manager.ts:375), gated on blocked/user-disabled servers (:59-67), then `McpClient.discoverInto` registers each `DiscoveredMCPTool` into the same registry (tools/mcp-client.ts:232-260). MCP tools get `<server>_<tool>` qualified names (mcp-tool.ts:557-561; prefix `mcp_` :37) used in schemas and policy. Server instructions are merged via `getMcpInstructions` (mcp-client-manager.ts:696).
- Skills are procedures, fetched on demand: `SKILL.md` frontmatter name/description loaded from dirs (skills/skillLoader.ts:115-127); only names go into the `activate_skill` declaration (tools/activate-skill.ts:170-172); activation returns the body as `<activated_skill>` llmContent and adds the folder to the workspace (:130-152). Sub-agents are tools of `Kind.Agent` (agents/agent-tool.ts).

## 3. Memory
- `HierarchicalMemory { global, extension, project, userProjectMemory }` (config/memory.ts:7-12). Discovery (utils/memoryDiscovery.ts): `~/.gemini/GEMINI.md` (:317), extension files (:383), upward walk cwd → project root (:458-509), `@file` imports (utils/memoryImportProcessor.ts:190). Injected into the system prompt as `<global_context>`, `<user_project_memory>`, `<extension_context>`, `<project_context>` (prompts/snippets.ts:553-570).
- Just-in-time: when read_file/replace/etc. touch a path, `discoverJitContext` loads that subdirectory's GEMINI.md into the tool output (tools/jit-context.ts:10-20; memoryDiscovery.ts:512).
- Private project memory: `~/.gemini/tmp/<hash>/memory/MEMORY.md` as an index pointing at sibling `*.md` (snippets.ts:88-93, :848); cross-project preferences go to the global file (:856). Writes use ordinary file tools guided by prompt text; tools/memoryTool.ts holds only filenames. Not found: a dedicated save_memory tool class.
- Auto-memory: `startMemoryService` (services/memoryService.ts:1133) runs at startup under a lock and min interval, indexes past session JSONLs (:665), runs a skill-extraction agent (agents/skill-extraction-agent.ts) whose `.patch` proposals land in an inbox validated by `validateMemoryInboxPatches` (:992).
- Sessions: JSONL via `ChatRecordingService` (services/chatRecordingService.ts:512), `/resume`, 1-line intent summaries (services/sessionSummaryService.ts:47-51), running topic title (config/topicState.ts:7-11).

## 4. Order of operations and approvals
- Per tool call, `Scheduler._processToolCall` (scheduler/scheduler.ts:612): BeforeTool hook (:619) → `checkPolicy` (:650) → DENY errors out; ASK_USER → `resolveConfirmation` (scheduler/confirmation.ts:110), which calls `shouldConfirmExecute` and awaits a correlated message-bus reply (:70-100) → `updatePolicy` on the outcome (scheduler.ts:692) → Cancel cascades to the whole batch (:704-711) → Scheduled → `_execute`.
- Tiers: `ApprovalMode` PLAN < DEFAULT < AUTO_EDIT < YOLO (policy/types.ts:48-64). Rules are TOML with priority bands default 1.x < extension 2.x < workspace 3.x < user 4.x < admin 5.x (policy/policies/write.toml:1-30); write tools `ask_user` at 10, autoEdit `allow` at 15 with an allowed-path safety checker (:33-50); plan mode denies all but explicit allows (plan.toml:20-25). `PolicyEngine.check` forces ASK_USER for commands outside the workspace, git in untrusted dirs, or dangerous commands (policy/policy-engine.ts:386-409); non-interactive default is DENY (:298-301).
- Outcomes (tools.ts:1106-1114): ProceedOnce / ProceedAlways (session) / ProceedAlwaysAndSave (persisted, scheduler/policy.ts:139-147) / ProceedAlwaysServer / ProceedAlwaysTool / ModifyWithEditor / Cancel. Labels: "Allow once", "Allow for this session", "Allow for this file in all future sessions", "No, suggest changes (esc)" (cli/src/ui/components/messages/ToolConfirmationMessage.tsx:288-400).
- Per-tool details union (tools.ts:986-1103): `edit` carries fileDiff/original/new; `exec` carries rootCommands/untrustedFlags/modifiedBuildFiles; `mcp` carries server+args; `info` URLs; `ask_user` questions; `exit_plan_mode` plan path. Shell always confirms when args came from untrusted context or a build file changed, even in YOLO (tools/shell.ts:310-322).
- Checkpoints: with checkpointing on, an edit call at AwaitingApproval triggers a shadow-git snapshot (`GitService.createFileSnapshot`, services/gitService.ts:196) plus a `<call>.json` with conversation history (utils/checkpointUtils.ts:94-142; useGeminiStream.ts:2226-2260). `/restore` reverts files and history (`restoreProjectFromSnapshot`, gitService.ts:216).

## 5. Steps and events to the UI
- Wire: `ServerGeminiStreamEvent` union (turn.ts:233-251), 18 `GeminiEventType`s (:55-74): Content, Thought, ToolCallRequest, ToolCallResponse, ToolCallConfirmation, UserCancelled, Error, ChatCompressed, MaxSessionTurns, Finished, LoopDetected, Citation, Retry, ContextWindowWillOverflow, InvalidStream (typed reasons :106-121), ModelInfo, AgentExecutionStopped/Blocked. `ToolCallRequest` ships a pre-built `display` (title/description from `tool.build(args)`) before anything runs (turn.ts:479-496).
- CLI: `processGeminiStreamEvents` switch (useGeminiStream.ts:1533-1680). Content appends to a pending `gemini` history item (:1116-1152); Thought sets the loading subject; tool calls become `IndividualToolCallDisplay` (cli/src/ui/types.ts:119-139) carrying `CoreToolCallStatus` validating/scheduled/awaiting_approval/executing/success/error/cancelled (scheduler/types.ts:81-187), mapped to Pending/Confirming/Executing/Success/Error/Canceled (types.ts:63-70).
- Global state: `StreamingState` Idle / Responding / WaitingForConfirmation (types.ts:50-54), derived from isResponding + tool statuses (useGeminiStream.ts:180-217).
- Progress: `LoadingIndicator` shows spinner + thought subject or a witty phrase cycling every 5s + "(esc to cancel, Ns)" (LoadingIndicator.tsx:62-76; usePhraseCycler.ts:12). Retry swaps in a retry phrase (useLoadingIndicator.ts:96); `useInactivityTimer` flags a 5s stall (useInactivityTimer.ts:16-20).
- Dead run: LoopDetected renders "A potential loop was detected... The request has been halted." (useGeminiStream.ts:1825). Not found: a wall-clock timeout on a pending confirmation; confirmation.ts:55-58 leaves it to the caller's signal.

## 6. Model portability
- `ContentGenerator` interface (core/contentGenerator.ts:39-61); `createContentGenerator` (:210) picks by `AuthType` (oauth, API key, Vertex, cloud-shell, ADC, gateway; :63-70) and wraps in Logging + ModelMapping generators (:298-300). Gemini-only in practice. `LocalLiteRtLmClient` (core/localLiteRtLmClient.ts:12-15) is a local JSON utility model, not the chat model.
- Per-turn routing: `ModelRouterService` composes Fallback → Override → ApprovalMode → Gemma/Classifier → Numerical → Default (routing/modelRouterService.ts:40-64); the classifier picks flash vs pro by estimated step count (routing/strategies/classifierStrategy.ts:31-40). Model is sticky for the rest of a prompt (client.ts:788-797); quota errors fall back to flash (availability/, useGeminiStream.ts:2160).
- Same across models: loop, tools, policy. Per-model: `tool.getSchema(modelId)` (tool-registry.ts:696), `tokenLimit(model)` (client.ts:672).

## 7. How they know it is good
- Behavioral evals (`evals/README.md`): test that the model *chooses* the right action; tagged `ALWAYS_PASSES` / `USUALLY_PASSES` (evals/answer-vs-act.eval.ts:21); e.g. ask_user.eval.ts, auto_memory_contract.eval.ts.
- `integration-tests/` with recorded `.responses` fixtures; `memory-tests/baselines.json`; `perf-tests/`.
- Telemetry: OTel + Clearcut loggers (core/src/telemetry/), events for loop detection (loopDetectionService.ts:233) and next-speaker checks (client.ts:880), `LlmRole` on every call (telemetry/llmRole.ts).

## 8. The feel: what the harness does so a normal model feels smarter than it is
- Anticipating the next step: `checkNextSpeaker` auto-continues when the model stopped mid-task (nextSpeakerChecker.ts:43-140; client.ts:876-899); `write_todos` keeps a visible plan (tools/write-todos.ts).
- Recalling unasked: hierarchical GEMINI.md plus JIT subdirectory context on file touch (jit-context.ts:10-20); startup extraction from old sessions (memoryService.ts:1133); MCP server instructions merged (mcp-client-manager.ts:696).
- Showing the work: Thought → loading subject (LoadingIndicator.tsx:67-68); tool description shown before execution (turn.ts:486); diff inside the confirmation (tools.ts:986-1000); elapsed time + esc hint.
- Never dead-ending: one self-correction nudge before halting (client.ts:1270); empty response → nudge + retry (geminiChat.ts:247-262); quota → flash; Cancel reads "No, suggest changes", turning a refusal into instructions (ToolConfirmationMessage.tsx:320).
- One good question: `ask_user` with choice (2-4 options) / text / yesno rendered as a card (tools/ask-user.ts:56-62; confirmation-bus/types.ts:182-186); `exit_plan_mode` carries approve/feedback payload (tools.ts:1013-1020).
- Continuity: JSONL sessions + `/resume` + summaries; `/restore` checkpoints; `ProceedAlwaysAndSave` persisting trust (scheduler/policy.ts:139-147).

## 9. The one thing to copy outright
**Copy:** the `ToolCallConfirmationDetails` union + `ToolConfirmationOutcome` scopes + the scheduler's hook → policy → confirm → updatePolicy sequence (tools/tools.ts:986-1114; scheduler/scheduler.ts:612-717). Each tool declares what the human must see (diff, command, server+args, question) and every approval carries a scope (once / session / forever / this server) the policy layer persists. For Corner: "send this reply?" with the draft as details, "always allow replies to X" as the saved rule.

**Avoid:** the UI-driven tool loop. `Turn` never executes tools; the React hook (useGeminiStream.ts:1972-2260) re-submits function responses and owns continuation, checkpointing and cancel state across ~2300 lines. Every non-terminal client (headless, mobile) must reimplement it. Corner should keep the loop server-side and stream events only.
