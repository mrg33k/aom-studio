# OpenClaw — structural brief

**Repo / source:** https://github.com/openclaw/openclaw at 120ad02b (v2026.9.4, shallow clone) · **Read on:** 2026-09-17 · **Reader:** Claude (corner:corner-v2 R82 harness study)
**One line:** An open-source personal agent daemon ("Gateway") that runs on the owner's own machine, answers in the chat apps they already use (Telegram, WhatsApp, Slack, iMessage, 20+), with any model, file-based skills, file+SQLite memory, a cron scheduler and owner-set rules — for one person or a small team.
**Why it is in the study:** It is the closest existing thing to Corner: one assistant reached over chat, working while the owner is away from a keyboard. It has solved approval-in-chat, progress-in-chat and proactive scheduling structurally, and its skills catalog is a drop-in replacement for a regex router.

Rules for this brief: structure over opinion. Every claim cites a file path (or a docs URL for closed products) and, where it helps, a short excerpt. Say "not found" rather than guess. Six sections, same order in every brief, so PATTERN.md can be built row by row.

## 1. The loop

**Message → turn.** A channel message enters `dispatchReplyFromConfig` (`src/auto-reply/reply/dispatch-from-config.ts:28`), which runs gather → prepare context → choose route → execute → finalize (imports at lines 7–16). Slash commands and inline directives (`/model`, `/queue`, `/approve`, `/elevated`) are handled before any model call (`src/auto-reply/reply/commands-*.ts`, `directive-handling.*.ts`). Runs are serialized per session lane, then a global lane capped by `agents.defaults.maxConcurrent` (`docs/concepts/queue.md`). A message that arrives mid-run is *steered* into the active run by default (mode `steer`, 500 ms debounce, cap 20, `drop: summarize`); other modes are `followup`, `collect`, `interrupt` (`docs/concepts/queue.md`, `src/auto-reply/reply/get-reply-run-queue.ts:16–48`).

**Who decides.** The model. The core loop is `packages/agent-core/src/agent-loop.ts:310–445`: an outer `while (true)` for queued follow-ups, an inner `while (hasMoreToolCalls || pendingMessages.length > 0)`. After each model response, tool calls are executed as a batch, results pushed to context (lines 427–430), and `hasMoreToolCalls` is recomputed from `stopReason === "toolUse"`, `endTurn === false`, or a continuation flag (lines 416–421). Steering messages are injected between batches (`pendingMessages`, line 422). There is no planner and no router in front of the model; the system prompt carries an **Execution Bias** section instead (`src/agents/system-prompt.ts:508–516`, excerpt: "Actionable request: act now. … Continue to done/real blocker; no plan-only finish when tools can act. … Final claim needs evidence or named blocker.").

**Budgets.** Time, not steps: default run timeout is 48 h (`DEFAULT_AGENT_TIMEOUT_SECONDS = 48 * 60 * 60`, `src/agents/timeout.ts:13`); model idle watchdog 120 s cloud / 300 s self-hosted / 60 s under cron (`src/agents/embedded-agent-runner/run/llm-idle-timeout.ts:28–34`). No max-steps counter found; the outer loop has a `MAX_RUN_LOOP_ITERATIONS` backstop referenced in a comment (`run/idle-timeout-breaker.ts:5`) whose definition I did not locate. Bolted-on guards: idle-timeout breaker trips after 5 consecutive idle timeouts with no output (`idle-timeout-breaker.ts:15`, comment cites a heartbeat that "generat[ed] 761–1384 paid Anthropic calls in 60 seconds"); tool-loop detection warns at 10 repeats, critical at 20, global circuit breaker at 30 over a 30-call window (`src/agents/tool-loop-detection.ts:51–54`, `tool-loop-thresholds.ts:1`). Approval waits pause the budget (`src/agents/agent-run-approval-wait.ts:44–60`); `ask_user` does not (`docs/concepts/agent-loop.md` "Timeouts").

**How a turn ends.** `stopReason: "stop"` with no tool calls. The silent token `NO_REPLY` is filtered out. If a required-reply turn ends after tools with no composed answer, a tool-free finalization pass runs; if the run ends on a tool failure with no reply, a fallback warning is sent so the user is never left with silence (`docs/concepts/agent-loop.md` "Reply shaping"; `run/tool-error-warning.ts:20–50`). Lifecycle `end`/`error` is emitted; a fallback is emitted by `agentCommand` if the loop did not.

**Across turns.** Transcript per agent in SQLite (`docs/openclaw-agent-runtime.md` state table). Near the context limit, a pre-compaction *memory flush* turn writes durable facts to `memory/YYYY-MM-DD.md` (`extensions/memory-core/src/flush-plan.ts:13–40`), then compaction summarizes older turns keeping ~20,000 recent tokens (`docs/concepts/compaction.md`). The system prompt is split at a cache boundary so the stable prefix is reused across channel turns (`src/agents/system-prompt.ts:1316`).

## 2. Skills and tools

**Tools** are typed schemas assembled per attempt (`run/attempt-tool-catalog.ts:48`), filtered by a policy pipeline (global/agent/channel/sender allow-deny; `src/skills/runtime/tool-dispatch.ts:1–30`) and by model compatibility (`filterLocalModelLeanTools`, schema quarantine, `attempt-tool-catalog.ts:19,26–27`). Plugins under `extensions/` register tools, providers, channels and hooks through `openclaw/plugin-sdk/*` (`extensions/anthropic/index.ts:10–17`); MCP servers attach as agent bundles (`src/agents/agent-bundle-mcp-*.ts`). Large catalogs use deferred schemas and a `tool_search` control (`system-prompt.ts:1099`).

**Skills** are `SKILL.md` files (AgentSkills spec) with YAML frontmatter `name`, `description`, and optional `metadata.openclaw.requires { bins, env, config }`, `os`, `user-invocable`, `disable-model-invocation`, `command-dispatch: tool` (`docs/tools/skills.md` "SKILL.md format", "Gating"; parser `src/skills/loading/frontmatter.ts:28–37`). Discovery walks seven precedence tiers — workspace `skills/` → `.agents/skills` → `~/.agents/skills` → managed → workshop → bundled (`skills/*`, e.g. `skills/weather`, `skills/summarize`) → plugin/extra dirs — and gates each at load time by binary/env/config presence and per-agent allowlist (`docs/tools/skills.md` "Loading order", "Agent allowlists"). `custodian-skills/` ships only to the system agent.

**Loaded into a turn: names, not bodies.** The prompt gets a compact `<available_skills><skill><name/><description/><location/></skill>…` catalog (`src/skills/loading/skill-contract.ts:122`, `workspace-skill-prompt.ts:173–174`), budgeted to 150 skills / 18,000 chars (`skill-prompt-limits.ts:10–11`, descriptions truncated first). The Skills section is seven lines (`src/agents/system-prompt.ts:268–275`): "Scan <available_skills>. Clear match: read exact <location> with `read`; obey. Several: most specific. None: read none. Up-front max one. Never invent paths." **Picking** is therefore the model's, and **loading** is a lazy `read` tool call on the SKILL.md. The skills list is snapshotted per session and refreshed on file change (`docs/concepts/agent-loop.md` "Session and workspace preparation"; `src/skills/runtime/refresh.ts`). Users can force selection with `$skill` references (max 8 per message, `src/skills/discovery/chat-command-invocation.ts:9`) or `/skill` slash commands; `command-dispatch: tool` skips the model entirely.

**Skill vs tool.** Skills are procedures that teach tool use; tools are calls. The agent may not write SKILL.md directly — it drafts a *Skill Workshop* proposal the operator reviews (`docs/tools/skills.md` "Skill Workshop"). Tool results return as `toolResult` messages, size-sanitized, with a live-result char cap derived from the context window (`run/attempt-exec-approval-continuation.ts:31`) and a `tool_result_persist` hook before transcript write.

## 3. Memory

**Tiers** (`docs/concepts/memory-architecture.md` "The tier model"):

| Tier | Surface | Written by | Loaded |
|---|---|---|---|
| Instructions | `AGENTS.md`, `SOUL.md`, `IDENTITY.md` | human | every session |
| Curated core | `MEMORY.md`, `USER.md` | dreaming consolidation, direct request | session start, budgeted |
| Episodic | `memory/YYYY-MM-DD.md`, transcripts | agent during work, flush, ingestion | never; `memory_search`/`memory_get` |
| Prospective | standing intents (SQLite), cron jobs | `intent` tool, scheduler | only when a trigger fires |
| Review | `DREAMS.md` | dreaming | never (human reading) |

**Up front.** Bootstrap files in order `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `BOOTSTRAP.md` (new workspace only), `MEMORY.md` (`docs/concepts/system-prompt.md` "Workspace bootstrap injection"; names `src/agents/workspace.ts:62–66`), capped 20,000 chars/file, 60,000 total, with a truncation notice injected. Daily notes are *not* injected on ordinary turns.

**On demand, zero model calls.** `memory_search` ranks hybrid relevance × 30-day half-life recency × write-time importance (`extensions/memory-core/src/tools.ts:434`; `memory-architecture.md` "Lane 1"). **Trigger injection:** curated entries carry `<!-- trigger: gateway setup, network safety --> <!-- importance: 9 -->`; each inbound message is prefiltered lexically/vector against triggers, and entries scoring ≥ 0.72 are injected as a hidden block, at most three per turn, curated tier only (docs; implementation file not located in this pass). **Escalation lane:** a blocking recall sub-agent runs only when the message shows recall intent *and* lane 1 found nothing strong (`extensions/active-memory/escalation.ts`; `docs/concepts/active-memory.md`).

**Writes.** One primary writer: *dreaming*, a cron-scheduled light → REM → deep sweep (`extensions/memory-core/src/dreaming-phases.ts`, `dreaming.ts:137–139`). Deep ranks candidates on recall frequency/diversity/recency, structurally excludes `untrusted` and `system` provenance, then a tool-free consolidation turn rewrites `MEMORY.md` (merge, supersede, dedupe) under an optimistic-concurrency hash check with the pre-image stored and a summary appended to `DREAMS.md` (`docs/concepts/dreaming.md` "Phase model"; `memory-architecture.md` "Write safety"). Feeds: the agent appending daily notes, the pre-compaction flush (`flush-plan.ts:16–19`: "Store durable memories only in memory/YYYY-MM-DD.md … APPEND … treat MEMORY.md … as read-only"), and session-end transcript ingestion. **Provenance** is SQLite columns the model cannot write (`owner | agent | untrusted | system`); cron/heartbeat/subagent sessions never yield durable candidates; recalled content is marked and never re-extracted; a network-sourced tool result taints the rest of the turn (`agent-loop.ts:415` `turnTainted ||= toolResults.some(toolResultTaintsTurn)`).

**Corrections.** "No hidden state": the owner edits the Markdown directly, or asks; `openclaw memory forget` removes entries derived from chosen sessions; cancelling a standing intent is durable state, never inferred from conversation (`docs/concepts/standing-intents.md` "List and cancel"). **Ledgers:** transcripts (SQLite), metadata-only audit ledger, cron run history, background-task ledger (`docs/automation/tasks.md`), and a per-session `progress_card`.

## 4. Order of operations and approvals

**Sequence.** Prompt-set, not code-enforced: Execution Bias (act now, live-check mutable facts, evidence before claiming done) and **Promised Work** (`src/agents/promised-work-prompt.ts:3–10`: "Before ending a turn, arrange an available completion or watch path … Proactively return with the result, link, proof, or a concrete blocker … Progress such as `running` is not completion."). Optional plan via `progress_card` (≤1 step `in_progress`).

**Tiers for host commands** — `tools.exec.mode` (`docs/tools/permission-modes.md`): `deny` · `allowlist` (run matches, silently deny misses) · `ask` (run matches, human on miss) · `auto` (run matches; an LLM reviewer judges misses → `allow` once / `deny` with a reason returned to the agent / `ask` a human; three consecutive reviewer denials escalate to a human) · `full`. Session-level modes `read-only | guarded | workspace | full` set the filesystem boundary and the reviewer (`docs/gateway/permission-modes.md` table) and can be changed mid-task; pending approvals from the old mode are cancelled, not granted.

**A risky action, in chat.** The exec tool registers a two-phase approval with the gateway and waits (`src/agents/bash-tools.exec-approval-request.ts:155–190`, `exec.approval.request` → `exec.approval.waitDecision`, with `expiresAtMs`); the run emits lifecycle `waiting-approval` and its time budget pauses (`agent-run-approval-wait.ts:44–60`). The channel plugin delivers a native card to the origin chat and/or the approver's DM (`src/infra/approval-native-delivery.ts:32–123`, surfaces `origin | approver-dm`, `notifyOriginWhenDmOnly`); Matrix seeds ✅ allow-once / ♾️ allow-always / ❌ deny reactions. Fallback is text: `/approve <id> allow|always|deny` (`src/auto-reply/reply/commands-approve.ts:18–31` aliases), accepted only from an authorized sender or `operator.approvals` scope (lines 147–176). `allow-always` mints a standing allowlist row in SQLite (`docs/tools/exec-approvals.md` schema, `"source": "allow-always"`), bound to the executable's real path/hash so a swapped binary is denied. A closed turn invalidates its pending approval; a late approval cannot restart it.

**Sends.** Messaging-tool sends are governed by tool allow/deny policy per channel/group/sender and a cancellable `message_sending` hook (`docs/concepts/agent-loop.md` hooks table); duplicates are suppressed. A dedicated "confirm before sending on the owner's behalf" card: not found.

**Questions.** `ask_user`: 1–3 structured questions, options in `options` with the recommended one first and suffixed "(Recommended)", `timeoutSeconds` default 900 (`src/agents/tools/ask-user-tool-normalization.ts:6`); "never ask whether to proceed or confirm a plan … If the result is no_answer, continue with best judgment" (`src/agents/tool-description-presets.ts:172–182`). A plain-text reply is routed to the pending question before ordinary queue handling (`src/auto-reply/reply/agent-runner-question-input.ts:31–60`).

**Loosen/tighten.** `/elevated on|full|off` per session gated by `tools.elevated.allowFrom` (`docs/tools/elevated.md`); `/exec security=… ask=…` per message can only tighten; `openclaw approvals`/`exec-policy` CLI; and *standing orders* in `AGENTS.md` — prose programs with Authority / Trigger / Approval gate / Escalation blocks that cron jobs reference (`docs/automation/standing-orders.md`). **Undo:** not found for chat actions; compaction "is not rollback", permission changes "do not undo completed writes"; only `MEMORY.md` rewrites keep a pre-image.

## 5. Steps and events to the UI

**Wire shape.** Three named streams per `runId`: `lifecycle` (`phase: "start" | "finishing" | "end" | "error"`, plus `waiting-approval` / `approval-resolved` carrying `approvalId`), `assistant` (text deltas), `tool` (`phase: "start" | "update" | "end"`, sanitized results) and `compaction` (`src/agents/embedded-agent-subscribe.handlers.lifecycle.ts:41–58`, `…tools.start.ts:491–503`, `…tools.completion.ts:435–453`, `…compaction.ts:41–43`). The `agent` RPC returns `{ runId, acceptedAt }` at once; `agent.wait` blocks up to 30 s and returns `ok | error | timeout` without cancelling (`docs/concepts/agent-loop.md`).

**Progress in a chat channel.** There is no token streaming to channels. Per channel `streaming.mode` is `off | partial | block | progress` (`docs/concepts/progress-drafts.md`). `progress` edits **one** message: a status headline, plan steps (✅ done / ▸ current / ▢ pending), approval requests, and optionally tool rows (`🛠️ Bash: run tests`), created 1.5 s after real work starts and finalized or replaced by the answer. Compositor `src/channels/progress-draft-compositor.ts:52` keeps the model's own preamble as headline for 20 s (`PROGRESS_STATUS_PREAMBLE_FRESH_MS`, line 45); event handlers for tool/item/approval/command-output at `progress-draft-events.ts:44–60`. When the main model is quiet, a cheap utility model narrates: at least 4 events, ≥ 12 s apart, ≤ 280 chars, ≤ 30 per turn (`src/auto-reply/reply/progress-narrator.ts:26–34`). Slow tools emit typed mid-call progress after a 5 s delay (`scheduleToolProgress`, docs). Typing indicators fire on enqueue and refresh every 6 s (`docs/concepts/typing-indicators.md`). `progress_card` is the durable status surface beside the session (`src/agents/tools/progress-card-tool.ts:35`).

**Stalls.** A running tool pings activity every 60 s (`run/tool-activity-heartbeat.ts:20–27`); the channel run-state machine republishes `busy` every 60 s (`src/channels/run-state-machine.ts:19`). Diagnostics classify a `processing` session with no reply/tool/status progress for 2 min as `session.long_running`, no recent progress as `session.stalled`, and abort-drain at ≥ 5 min and 3× the warning threshold (`docs/concepts/agent-loop.md` "Stuck session diagnostics"; `src/logging/diagnostic-stability.ts:329–330`). Retryable errors get a 15 s grace for fallback; a definitive timeout finalizes the chat as `error`/`aborted` with the timeout explanation retained (a failed turn, not a success).

## 6. Model portability

**Abstraction.** `src/llm/stream.ts:84–121` exposes `stream | complete | streamSimple | completeSimple(model, context, options)` over a provider registry; a `Model` carries `api`, `provider`, `id` (lines 36–40). Every provider is a plugin under `extensions/<provider>/` (anthropic, openai, google, ollama, openrouter, litellm, vllm, llama-cpp, lmstudio … ~60) whose `openclaw.plugin.json` declares `providers`, a `modelCatalog` (`api`, `contextWindow`, `maxTokens`, `cost`, `thinkingLevelMap`, `compat`), aliases (`"opus": "claude-opus-5"`) and auth choices (`extensions/anthropic/openclaw.plugin.json`). A local Claude CLI login can be reused as a backend (`extensions/anthropic/cli-backend.ts`).

**Identical across models:** the system prompt ("OpenClaw builds its own system prompt for every agent run; there is no runtime default prompt", `docs/concepts/system-prompt.md`), tools, loop, memory, channels. **Per model/provider:** a provider may replace exactly three named prompt sections (`interaction_style`, `tool_call_style`, `execution_bias`) and add a stable prefix above / dynamic suffix below the cache boundary (docs); per-provider request params (`embedded-agent-runner/extra-params.ts`), compat shims (`model.compat.ts`), thinking-level maps, context windows, lean tool sets for small local models and schema quarantine (`attempt-tool-catalog.ts:19–27`).

**Switching.** `/model provider/model` in chat or the picker writes a strict user override (no fallback); config `agents.defaults.model.primary` + `fallbacks[]`; cron `--model`. On failure: bounded same-model recovery → auth-profile rotation → next fallback model, turn-local, never persisted as the selection (`docs/concepts/model-failover.md` "Runtime flow"; `run/failover-policy.ts:1–80`). Alternate harnesses (Codex app-server) plug in via `agentRuntime.id` (`docs/agent-runtime-architecture.md` "Runtime Selection").

## 7. How they know it is good

A private QA lab drives YAML scenarios (`qa/scenarios/<theme>/*.yaml`, `qa/README.md`) through a synthetic `qa-channel` and a `mock-openai` provider. The **Personal Agent Benchmark Pack** is ten scenarios — reminder round-trip, thread reply, preference recall, no secret leak, tool-safety follow-through, approval-denial stop, task status honesty, share-safe diagnostics, *no fake progress*, failure recovery — each bound to a coverage ID in the maturity scorecard `taxonomy.yaml:24–35` (`docs/concepts/personal-agent-benchmark-pack.md`). Prompt snapshots are drift-checked in CI (`pnpm prompt:snapshots:check`); live provider tests sit behind `OPENCLAW_LIVE_TEST=1`; `qa/frontier-harness-plan.md` is a big-model bake-off. Dogfooding: "We build OpenClaw with OpenClaw on team.openclaw.ai" (`VISION.md`). No usage telemetry by default (`VISION.md` "Security"). Memory design cites LongMemEval and Generative Agents rather than in-house evals.

## 8. The feel: what the harness does so a normal model feels smarter than it is

- **Anticipating the next step.** Code-owned prompt sections Execution Bias and Promised Work (`system-prompt.ts:508`, `promised-work-prompt.ts:3–10`); the agent owns an `automations` tool and is told to use cron, not sleep loops, for "check back later" (`docs/concepts/system-prompt.md` "long-running-work guidance"); **standing intents** — the `intent` tool stores event-conditioned reminders in SQLite, matched by FTS prefilter on every turn with no model call, cooldown 24 h, max 3 fires, 90-day expiry, at most 3 injected (`extensions/memory-core/src/standing-intents-tool.ts`, `standing-intents.ts:19`); **heartbeat** every 30 m in the main session with a narrow prompt and a `NO_REPLY` / `heartbeat_respond notify:true|false` contract so quiet stays quiet (`src/auto-reply/heartbeat.ts:8–24`); standing orders in `AGENTS.md`.
- **Recalling the right thing unasked.** `MEMORY.md`/`USER.md` bootstrap each session; trigger-phrase injection of ≤ 3 curated entries; project-scoped memory boosts; the deep recall sub-agent only when the message asks about the past (§3).
- **Showing the work.** The single edited progress message with plan steps and utility-model narration; `progress_card`; typing on enqueue (§5).
- **Never dead-ending.** Tool-free finalization pass; fallback warning that names partial results ("timed out after Ns; 3 partial results are available", `run/tool-error-warning.ts:26–35`); `ask_user` "no_answer → continue with best judgment"; reviewer `deny` returns a *reason* so the agent picks a safer route; overflow → compact and retry; model fallback chain; prompt line "Weak/empty result: vary query/path/command/source, then conclude".
- **One good question.** `ask_user` contract: one question, choices as options, recommended first, never "shall I proceed" (§4).
- **Continuity.** Per-agent SQLite transcript with `/new`/`/reset` boundaries; memory flush before compaction; dreaming consolidation; `SOUL.md` persona and `BOOTSTRAP.md` first-run conversation (`src/agents/bootstrap-prompt.ts`); auth profile pinned per session to keep provider caches warm (`docs/concepts/model-failover.md` "Session stickiness").

## 9. The one thing to copy outright

**Copy:** the lazy skills catalog — `SKILL.md` files with `name`/`description` frontmatter, rendered as a budgeted `<available_skills>` list of name + description + location, and a seven-line prompt contract that makes the model pick a skill and `read` it only on a clear match (`src/agents/system-prompt.ts:268–275`, `src/skills/loading/skill-contract.ts:122`, `skill-prompt-limits.ts:10–11`). It replaces Corner's regex router with model-chosen procedures at ~18k chars of catalog cost, uses a public spec Corner can author today, and gives every procedure a file the owner can read and edit. Runner-up: the two-phase approval with a stable id, native card + `/approve <id> allow|always|deny` fallback, budget pause and allow-always → allowlist (§4).

**Avoid:** a time-only run budget. OpenClaw's loop is bounded by a 48-hour wall clock and provider idle watchdogs, with no per-turn step budget (`src/agents/timeout.ts:13`); it then had to bolt on an idle-timeout breaker after a single heartbeat burned "$20–30 per incident" (`run/idle-timeout-breaker.ts:11–15`) and a three-tier tool-loop detector. Corner should start with a small explicit step/tool budget per turn and a hard "partial result + offer" on exhaustion, and grow it deliberately.
