# goose — structural brief

**Repo / source:** github.com/aaif-goose/goose (started at Block, now Agentic AI Foundation / Linux Foundation, `README.md`) at commit `d213a3b1` (2026-09-17), read from the shallow clone · **Read on:** 2026-09-17 · **Reader:** goose reader (corner:corner-v2 R82)
**One line:** an open-source, Rust, general-purpose agent (desktop app, CLI, ACP server) whose every capability is an MCP server and whose approvals are a per-tool tier stack.
**Why it is in the study:** the cleanest existing answer to "tools are MCP, approvals are tiers, the ask is just another message in the stream" — the three things Corner's one-completion-per-turn chat lacks.

Rules for this brief: structure over opinion. Every claim cites a file path relative to the goose repo root. "Not found" over guessing.

## 1. The loop
`Agent::reply` (`crates/goose/src/agents/agent.rs:2044`) returns a `BoxStream<Result<AgentEvent>>`. Two implementations coexist: the legacy `reply_internal` (`agent.rs:2416`) and an ordered-operations state machine behind `GOOSE_STATE_MACHINE=1` (`agents/state_machine/mod.rs:76`; `AGENTS.md` "Agent Loop Migration": "we are replacing the legacy agent loop"). Both are model-driven: no planner or router; the model returns text or tool requests and the harness executes and re-prompts.

Legacy turn: `prepare_reply_context` (`agent.rs:844`) repairs the conversation (`fix_conversation`), builds the tool list and system prompt; a per-turn context message is persisted (`agents/moim.rs:81`: time, cwd, compaction status, turn budget); then `loop` at `agent.rs:2586` — stream the provider (`agent.rs:2687`), split tool requests from text (`categorize_tool_requests`), inspect, approve, dispatch, append tool responses as user messages, repeat while tool requests exist.

Budgets: `DEFAULT_MAX_TURNS = 1000` / `GOOSE_MAX_TURNS` (`agent.rs:85, 2673`, exhaustion yields `MAX_TURNS_MESSAGE`); `MAX_EMPTY_TURN_RETRIES = 3` (`agent.rs:88, 3388`); two compaction attempts before "Unable to continue" (`agent.rs:3130`); 300 s per tool call (`config/extensions.rs:10`, `agents/mcp_client.rs:945`). A turn ends on no tool requests, on the recipe `final_output` tool (`agent.rs:2620`), on a Stop hook Allow (`agent.rs:2632`), or cancel.

State-machine order (`agent.rs:1687-1735`): EntryHook → SlashCommand → Steer → MaxTurns → BangShell → Compaction → ToolPairCompaction → ToolApproval → Doctor → Project → Skill → Recipe → ToolExecution → UnknownTool → Retry → StopHook → ExitOnError, iterated in order by `crates/goose-agent/src/machine.rs:77`. Between turns everything lives in the session (section 3).

## 2. Skills and tools
**MCP is the only tool model.** `ExtensionConfig` variants: `Stdio`, `Builtin`, `Platform`, `StreamableHttp` (`agents/extension.rs:156-208`). Built-ins are real MCP servers in `crates/goose-mcp/src/` (memory, computercontroller, autovisualiser, tutorial); platform extensions run in-process but through the same client trait (`agents/platform_extensions/`: todo, chatrecall, summon, scheduler, apps).

Discovery: `McpClientTrait::list_tools` sends `ListToolsRequest` (`agents/mcp_client.rs:884`); `ExtensionManager::get_prefixed_tools` (`agents/extension_manager/mod.rs:671`) returns the cached, `extension__tool`-prefixed list. **All tools are loaded up front every turn** (`agent.rs:862`); docs warn "fewer than 25 total tools" (`documentation/docs/guides/managing-tools/tool-permissions.md`). Each extension's `instructions` go into the system prompt under `## {{extension.name}}` (`prompts/system.md`, `agents/prompt_manager.rs:108-150`). Selection is native tool calling; `providers/toolshim.rs:1-31` emulates it with an interpreter model for models without it.

Result path: `dispatch_tool_call` (`extension_manager/mod.rs:1243`) → `call_tool` (`mcp_client.rs:908`) under a `select!` of result / timeout / cancel (`mcp_client.rs:945-953`). It returns `ToolCallResult { result, notification_stream, action_required_stream }` (`agents/tool_execution.rs:77-81`), merged into `ToolStreamItem::{ActionRequired, Message, Result}` (`tool_execution.rs:104-108`). The result is written into a user message via `add_tool_response_with_metadata` keyed by request id (`agent.rs:2779, 2898`); tool errors are returned as tool results, "the errors become prompts" (`documentation/docs/goose-architecture/extensions-design.md`). Responses over 200k chars are written to a file and replaced by a pointer (`agents/large_response_handler.rs:5-36`).

Skills vs tools: Agent-Skills-spec `SKILL.md` files under `~/.agents/skills` and `<project>/.agents/skills` (`skills/mod.rs:47-55`) are served through a runtime MCP client (`skills/mod.rs:10`), so a skill is a tool too. Recipes (section 8) are the procedural layer. Hooks: `PreToolUse … Stop` (`hooks/mod.rs:55-68`).

## 3. Memory
Sessions are SQLite (`session/session_manager.rs:19, 714`); every message is persisted as it is produced, compaction calls `replace_conversation`, per-session extension state is saved (`agent.rs:2953`). Auto-naming after ≤3 user messages (`session_manager.rs:644-660`, `prompts/session_name.md`).

Up front: `.goosehints` and `AGENTS.md` (global `~/.config/goose/.goosehints` + project) into the system prompt (`hints/load_hints.rs:10-24`, `prompt_manager.rs:86-96`); subdirectory hints load lazily when a tool touches a path (`load_hints.rs:42`, `prompt_manager.rs:212-236`). The memory MCP server appends **all global memories into its own instructions** at startup (`crates/goose-mcp/src/memory/mod.rs:156-170`), so they reach the prompt without a call; tools `remember_memory` / `retrieve_memories` (`memory/mod.rs:390-454`), local `.goose/memory/` vs global (`memory/mod.rs:119-127`), "Always confirm with the user before saving". Corrections: "if the user removes a memory … remove it from the system instructions" (`memory/mod.rs:152`). On demand: `chatrecall` searches past sessions by keyword or id (`platform_extensions/chatrecall.rs:5-19`). Ledger: `todo__todo_write` (`platform_extensions/todo.rs:5-7`). Compaction summaries replace history and the continuation text forbids mentioning them (`context_mgmt/mod.rs:33-36`).

## 4. Order of operations and approvals
No gather/plan/act phases beyond the ops list in section 1. Modes: `GooseMode::{Auto (default), Approve, SmartApprove, Chat}` (`crates/goose-provider-types/src/goose_mode.rs:22-32`; docs table `guides/managing-tools/goose-permissions.md`). Per-tool `PermissionLevel::{AlwaysAllow, AskBefore, NeverAllow}` (`config/permission.rs:21-25`), two maps (user rules, smart-approve cache) via `PermissionManager` (`permission.rs:77-82, 160-165`).

Decision stack, `PermissionInspector::inspect` (`permission/permission_inspector.rs:150-205`): Chat → skip; Auto → allow; else (1) user rule, (2) SmartApprove + MCP `read_only_hint` → allow, (3) `manage_extensions` always asks, (4) SmartApprove and uncached → LLM judge, (5) default ask. The judge `detect_read_only_requests` (`permission/permission_judge.rs:150-186`) is one `provider.complete` with a single tool `platform__tool_by_tool_permission` whose prompt treats ids and args as untrusted; non-read-only verdicts are cached as AskBefore (`permission_inspector.rs:22-33`); `read_only_hint == false` annotations bulk-cache AskBefore (`config/permission.rs:91-107`). Output is `PermissionCheckResult { approved, needs_approval, denied }` (`permission_judge.rs:189-194`); security inspectors override (`permission_inspector.rs:118-128`).

The ask: `handle_approval_tool_requests` (`tool_execution.rs:149-240`) yields an assistant message `ActionRequired::ToolConfirmation { id, tool_name, arguments, prompt }` marked `.user_only()` (never sent to the model), then awaits a oneshot from `tool_confirmation_router` (`tool_execution.rs:172-185`). Answers: `Permission::{AlwaysAllow, AllowOnce, Cancel, DenyOnce, AlwaysDeny}` (`goose-provider-types/src/permission.rs:5-11`); Always* writes a rule back (`tool_execution.rs:218-236`); a denial becomes a tool result `DECLINED_RESPONSE` so the model knows (`tool_execution.rs:226-230`). Asks are sequential; a turn lock forbids two concurrent turns per session (`agents/tool_confirmation_coordinator.rs:37-47`). Chat mode returns a "skipped" tool result (`agent.rs:2852-2868`).

User controls: `/mode auto|smart_approve|approve|chat`, desktop mode button, `goose configure → Tool Permission` (docs above). An arg-hashed, expiring `ToolPermissionStore` exists (`permission/permission_store.rs:11-20, 79-90`); its wiring into the inspector: not found. Undo/rollback: not found in core (text-editor undo lives in the developer extension, `goose-self-test.yaml:9`). Stop hooks can deny turn end up to a cap (`agent.rs:2632-2660`).

## 5. Steps and events to the UI
One enum: `AgentEvent::{Message, Usage, MessageUsage, McpNotification((request_id, ServerNotification)), HistoryReplaced(Conversation)}` (`crates/goose-agent/src/events.rs:9-18`). A step, a tool call, a question and a progress line are all `Message`s of content blocks: `Text, Image, Document, ToolRequest, ToolResponse, ToolConfirmationRequest, ActionRequired, Thinking, RedactedThinking, SystemNotification, Error` (`goose-provider-types/src/conversation/message.rs:318-330`); chunks share a message id (`agent.rs:2063`). Progress is `SystemNotification` with `InlineMessage` / `ProgressMessage` (`agent.rs:3132-3145`); MCP progress notifications drive the spinner text (`goose-cli/src/session/output.rs:350-359`).

There is no goose-server crate now; the desktop and editors speak ACP (`crates/goose/src/acp/server.rs`; `ui/desktop/src/acp/chatNotifications.ts:12`). Mapping (`server.rs:2147-2220, 1379-1400`): text → `AgentMessageChunk`, thinking → `AgentThoughtChunk`, tool request/response → `ToolCall` / `ToolCallUpdate` (`acp/tool_call_notifier.rs:20-37`), `ToolConfirmation` → ACP `request_permission` (`server.rs:1407-1420`, `acp/common.rs:55-98`), `Elicitation` → a form (`server.rs:1425`). Provider streaming yields `(Option<Message>, Option<ProviderUsage>)` (`goose-provider-types/src/base.rs:327-329`).

Dead runs: tool timeout → error result; provider retries are exponential and transient-only (`goose-provider-types/src/retry.rs:14-26`); `RepetitionInspector` stops identical repeated calls (`tool_monitor.rs:33-39`); empty responses retry 3× then a visible `EMPTY_TURN_MESSAGE` (`agent.rs:3388-3404`); cancel tokens thread every `select!`.

## 6. Model portability
`Provider` trait (`crates/goose-provider-types/src/base.rs:464-540`): `stream()` is the only required method; `complete()`, `get_context_limit`, `retry_config`, `fetch_supported_models`, `manages_own_context`, `provider_session_id`/`resume` have defaults. A registry of constructors (`providers/provider_registry.rs:12-35`) serves ~50 providers (`providers/`), plus declarative ones (`crates/goose-providers/src/declarative.rs`) and ACP agents as providers (`providers/claude_acp.rs`, `codex_acp.rs`; docs `guides/acp-providers.md`).

Identical across models: `prompts/system.md`, rmcp `Tool` schemas, the loop, permissions, compaction, session store. Per-model: wire formats (`goose_providers::formats::*`), context-limit resolution via a canonical registry (`base.rs:499-503`), thinking replay quirks (`agent.rs:2955` "DeepSeek and Kimi need the turn's thinking on every split"), toolshim, `manages_own_context` (ACP providers skip compaction, `context_mgmt/mod.rs:232`). Switching: `/model` mid-session (`guides/multi-model/index.mdx`), `Agent::update_provider` (`agent.rs:3590`), recipe `settings.goose_provider/goose_model` (`recipe/mod.rs:99-111`), model config stored per session (`permission_judge.rs:14-20`). Automatic model fallback: not found. Side calls (judge, compaction, naming) reuse the session provider via `complete_one_shot` (`context_mgmt/mod.rs:288-297`).

## 7. How they know it is good
`evals/harbor/` runs terminal-bench-2 (89 tasks) across goose builds and rival harnesses, reporting pass rate, compute hours, tokens, turns, cost (`evals/harbor/README.md:1-45`: stock goose 50.6 %, code-mode 57.3 %). `goose-self-test.yaml` is a recipe in which goose tests its own tools (`AGENTS.md` requires updating it per feature). Opt-in PostHog telemetry (`posthog.rs:16-40`) emits provider error classes (`agent.rs:3127`); OpenTelemetry `gen_ai` spans (`agent.rs:2077-2085`); security-decision counters (`tool_execution.rs:186-197`). Scenario tests in `crates/goose-cli/src/scenario_tests/`.

## 8. The feel: what the harness does so a normal model feels smarter than it is
- **Orientation every turn**: the turn-context block (`moim.rs:9-22, 81`) gives time, cwd, remaining context and turn budget, with "as the budget gets low, become more direct".
- **Invisible memory of the long chat**: auto-compaction at 80 % (`context_mgmt/mod.rs:225-275`), background tool-pair summarization (`mod.rs:493`), recovery compaction on `ContextLengthExceeded` (`agent.rs:3124-3170`), and a continuation text that forbids saying "summary" (`mod.rs:33-36`).
- **Recalling unasked**: global memories inside extension instructions (`memory/mod.rs:156-170`); hints that load when a directory is touched (`load_hints.rs:42`); `chatrecall` for older sessions.
- **Never dead-ending**: errors as tool results; empty-turn retry then a visible message; a context-limit message that lists three exits (`agent.rs:3132`); big outputs to a file instead of truncation (`large_response_handler.rs:31-36`).
- **One good question**: MCP elicitation surfaces `ActionRequired::Elicitation { message, requested_schema }` as a form (`message.rs:204-208`, `elicitation.rs`, `server.rs:1425`); tool asks offer four answers, not yes/no (`goose-cli/src/session/mod.rs:2164-2218`).
- **Showing work**: spinner with rotating messages (`output.rs:161-183`), MCP progress → spinner text, ACP `ToolCall` status, chain summaries for consecutive tool runs (`server.rs:2192`).
- **Continuity**: SQLite sessions, auto-names, provider-session resume (`agent.rs:2445-2452`), mid-turn steering (`agent.rs:2591`, `state_machine/ops_steer.rs`).
- **Recipes** (`recipe/mod.rs:43-87`): title, description, instructions, prompt, extensions, settings (model, max_turns), `activities` (starter pills), `parameters`, `response` JSON schema (→ `final_output_tool.rs`), `sub_recipes`, `retry` with shell success checks and `on_failure` (`agents/types.rs:16-31`). Slash commands run them; the scheduler runs them on cron (`platform_tools.rs:4` `manage_schedule`). `summon` adds `load`/`delegate` subagents (`platform_extensions/summon.rs:707, 780`).

## 9. The one thing to copy outright
**Copy:** the approval stack plus the ask-as-a-message: `permission/permission_inspector.rs:150-205` (user rule → read-only annotation → cached LLM read-only judge → default ask) feeding `tool_execution.rs:149-240` (yield a `ToolConfirmation` message the model never sees, await one of five answers, write Always* back as a rule, return a denial to the model as a tool result). Corner's send/pay/delete tools need exactly this, and it is a few hundred lines with no dependency on the loop shape.

**Avoid:** the legacy loop-with-flags — `reply_internal` in a 6,161-line `agent.rs` holds ~15 mutable booleans per turn (`agent.rs:2542-2560`) and goose itself is retiring it for the ordered operations list (`AGENTS.md`; `state_machine/mod.rs`). Start Corner from the ordered ops list, never from the loop. Secondary: do not load every tool into every turn (goose's own "<25 tools" warning).
