# Cline (+ Roo Code) — structural brief

**Repo / source:** github.com/cline/cline at 48285af (2026-09-16); github.com/RooCodeInc/Roo-Code at b867ec9 (2026-05-15) · **Read on:** 2026-09-17 · **Reader:** Claude (corner:corner-v2 R82)
**One line:** Cline is a VS Code coding agent whose loop moved (2026) into an embeddable SDK (`sdk/packages/agents`) fronted by a hub daemon; Roo Code is the fork that kept the classic in-extension loop and added modes.
**Why it is in the study:** the cleanest example of a typed ask/say message stream where every step, tool call, question and failure is a row the UI can render and answer, with an auto-approval decision function in front of every human touchpoint.

Rules for this brief: structure over opinion. Every claim cites a file path (or a docs URL for closed products) and, where it helps, a short excerpt. Say "not found" rather than guess. Six sections, same order in every brief, so PATTERN.md can be built row by row.

## 1. The loop

**Cline (SDK).** `Agent.run` in `sdk/packages/agents/src/agent-runtime.ts:763-931`: `while (maxIterations === undefined || iteration < maxIterations)`: emit `turn-started`, call the model with retry (`generateAssistantMessageWithProviderRetry`, :1033-1067), push the assistant message, then branch. No tool calls → either inject completion reminders and continue (:851-866) or `finishRun("completed")` (:867-873). Tool calls → `executeToolCalls` (sequential or parallel, :1880-1898), then `findCompletingToolMessage`: a tool declaring `lifecycle.completesRun` (`submit_and_exit`, `sdk/packages/core/src/extensions/tools/definitions.ts:843-856`, the "SDK analog of attempt_completion" per `sdk/ARCHITECTURE.md`) ends the run (:1901-1919). Exceeding `maxIterations` throws → `run-failed` (:928-930); no default found (`agent-runtime-config-builder.ts:126` passes it through). The model decides the next action; no planner or router. Guards: `MistakeTracker` max 6 consecutive (`sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts:434`), loop detection soft 3 / hard 5 identical calls (`runtime/safety/loop-detection.ts:113-116`), provider retry 3× with 1s→15s backoff only when nothing streamed yet (`agent-runtime.ts:66-70, 1076-1100`), one compact-and-retry on context overflow (:1146-1190).

**Roo (classic).** `initiateTaskLoop` (`src/core/task/Task.ts:2427-2459`) wraps `recursivelyMakeClineRequests` (:2461), an explicit stack. If the model answers without a tool it gets `formatResponse.noToolsUsed()` and after two in a row it counts as a mistake (:3480-3500); mistake limit 3 (`packages/types/src/provider-settings.ts:29`) → `ask("mistake_limit_reached")` (:2483-2500). `attempt_completion` ends by `ask("completion_result")`; user feedback pushes a tool result and the loop continues (`src/core/tools/AttemptCompletionTool.ts:131-142`). Auto-approve ceilings on request count and dollar cost (`src/core/auto-approval/AutoApprovalHandler.ts:51, 99`).

**Across turns:** the full API history persists (`api_conversation_history.json`, `ui_messages.json`, `src/shared/globalFileNames.ts`); Cline's `ConversationStore` persists lazily on first user turn (`sdk/packages/core/src/session/stores/conversation-store.ts`; `ARCHITECTURE.md` "Root-session persistence is lazy").

## 2. Skills and tools

Cline tools are `AgentTool` objects with zod→JSON schemas, registered from `config.tools` + plugins at run start (`agent-runtime.ts:655-666`); defaults: `read_files`, `search_codebase`, `run_commands`, `fetch_web_content`, `apply_patch`, `editor`, `skills`, `ask_question`, `submit_and_exit` (`definitions.ts:272-856`). MCP: `McpHub` calls `tools/list` per server with per-server timeout, marks `autoApprove` from `mcp_settings.json` (`apps/vscode/src/services/mcp/McpHub.ts:884-898`), coalesces `list_changed` refreshes (:135, :1012); exposed to the model as `server__tool` (`apps/vscode/src/sdk/sdk-tool-policies.ts:88-89`). Skills are `SKILL.md` files (`extensions/config/user-instruction-config-loader.ts:36`) invoked lazily through one `skills` tool whose description says a matching skill is "a blocking requirement before any other response" (`definitions.ts:765-769`). Tool results return as `tool-result` messages (`agent-runtime.ts:876-883`); a denied tool returns an error result with `TOOL_REJECTION_SUFFIX` (:2007). Roo scopes tools per mode via `TOOL_GROUPS` (`src/shared/tools.ts:297-312`) and checks `validateToolUse` before each call (`src/core/assistant-message/presentAssistantMessage.ts:584`).

## 3. Memory

Rules files: Cline loads `.clinerules`, `.cline/*.md`, workspace and global `AGENTS.md` (`user-instruction-config-loader.ts:549-567, 674-676`; `shared/src/storage/paths.ts:50, 531`) into a `# Rules` section (`runtime/safety/rules.ts:10-20`). Roo: `.roo/rules/`, `.roo/rules-<mode>/`, `AGENTS.md`/`AGENTS.local.md`, legacy `.roorules` (`src/core/prompts/sections/custom-instructions.ts:206-229, 279-318, 409`). "Memory Bank" is a documented convention, not code: six markdown files driven by the phrases "initialize/update memory bank" (`docs/best-practices/memory-bank.mdx`). No built-in cross-session memory found in either codebase. Roo appends `<environment_details>` to every user message (visible files, terminals, "Recently Modified Files", time, cost, mode, todo reminders; `src/core/environment/getEnvironmentDetails.ts:44-265`) and strips the stale block first (`Task.ts:2400-2413`). Compaction: Cline triggers at 0.9 of max input, targets 0.7, preserves 20k recent tokens (`extensions/context/compaction-shared.ts:13-27`); the LLM-summary strategy is skipped for overflow recovery, which "must not depend on another successful LLM request" (`compaction.ts:44-52`); summaries carry `displayRole: "system"` so they never render (`agent-runtime.ts:889-901`). Roo condenses at `autoCondenseContextPercent` or within a 10% buffer (`src/core/context-management/index.ts:24, 171-192`) and tags the summary with `isSummary`/`condenseId` so history filtering survives restores (`src/core/condense/index.ts:539`). Cline also keeps a SQLite agenda of typed tasks (`suggestion`, `follow-up`, `todo`, `handoff`, `reminder`) with a `pending_approval` status (`sdk/packages/core/src/tasks/agenda-task-tool.ts:16-33`) plus a cron service (`core/src/cron/`).

## 4. Order of operations and approvals

**Order.** Cline's is prompt-only: gather → plan → act → verify (`sdk/packages/shared/src/prompt/system/act.ts`); Plan/Act is a UI mode (`plan_mode_respond`/`act_mode_respond` asks, `apps/vscode/src/shared/ExtensionMessage.ts:211-212`) with a guard that blocks commands in plan mode (`apps/vscode/src/sdk/message-translator.ts:1898-1901`). Roo makes it structural: modes are ordered configs with tool groups and file-regex limits, e.g. Architect may edit only `\.md$` and must end with `switch_mode` (`packages/types/src/mode.ts:168-230`); `switch_mode`/`new_task` are always available (`tools.ts:310-312`); Orchestrator has no tool groups at all (`mode.ts:214-220`); violations raise `FileRestrictionError` (`src/shared/modes.ts:135-145`); users add modes in `.roomodes` (`src/core/config/CustomModesManager.ts:19`).

**Tiers.** Cline: per-tool `{enabled, autoApprove}` policy with a `*` wildcard (`agent-runtime.ts:187-196`) resolved before execution; `autoApprove:false` calls the host's `requestToolApproval` callback (:1993-2060). The VS Code host forces read/edit/command/web/MCP tools to ask and evaluates the live toggles inside the callback so mid-task changes apply (`sdk-tool-policies.ts:13-66`); settings are five booleans, defaults read/edit/browser/MCP on, safe-commands off (`apps/vscode/src/shared/AutoApprovalSettings.ts:14-43`). The hub brokers approvals as `approval.requested`/`approval.resolved` events so any attached client can answer (`hub/server/handlers/approval-handlers.ts:38-58, 113`); the desktop path polls a decision file with a 5-minute timeout (`runtime/tools/tool-approval.ts:74-101`). `PreToolUse` hooks may rewrite input, override policy or skip (`agent-runtime.ts:1959-1985`). Roo: `checkAutoApproval` returns `approve | deny | ask | timeout` (`src/core/auto-approval/index.ts:37-45`) over categories read/write/MCP/mode-switch/subtasks/execute/follow-up with outside-workspace and protected sub-flags (:17-35), command allow/deny lists (:114-120), and a follow-up that auto-picks the first suggestion after a timeout (:66-83); the decision runs inside `Task.ask` (`Task.ts:1316-1327`).

**Checkpoints.** Roo: shadow git with `core.worktree` pointed at the workspace (`src/services/checkpoints/ShadowCheckpointService.ts:177`), saved before every edit tool (`presentAssistantMessage.ts:653-688`) and on every user message (`Task.ts:1464-1469`); restore rewinds messages and reports deleted cost (`src/core/checkpoints/index.ts:234-298`). Cline SDK: stash-style snapshots incl. untracked files under `refs/cline/checkpoints/<session>/` (`core/src/hooks/checkpoint-hooks.ts:342-407, 449`); restore is a transaction with rollback (`session/checkpoint-restore.ts:50-150`); three restore options, Files / Task / both (`docs/core-workflows/checkpoints.mdx`).

## 5. Steps and events to the UI

Wire shape: `ClineMessage { ts, type: "ask"|"say", ask?, say?, text, partial, seq, epoch, lastCheckpointHash }` (`ExtensionMessage.ts:177-207`); 18 ask kinds (:209-227), 37 say kinds (:229-266). `ts` is identity: a `partial` update upserts the same row (`Task.ts:1240-1258`). Cline SDK events (`run-started`, `turn-started`, `assistant-text-delta`, `tool-started/updated/finished`, `status-notice`, `run-finished/failed`) become session events `iteration_start`, `content_start/update/end`, `notice`, `usage`, `done`, `error` (`runtime/orchestration/runtime-event-adapter.ts:187-262`), then ClineMessages (`message-translator.ts:1272-1970`): `iteration_start` → `say:api_req_started` spinner (:1780-1795); approval → `ask:tool|command|use_mcp_server|use_subagents` (:1134-1183); compaction notice → live divider row (:1803-1834); command output streams via `emitUpdate` → `content_update` (`agent-runtime.ts:2096-2103`). Failure: `error` → `say:api_req_started{streamingFailedMessage}` replacing the spinner, then `ask:api_req_failed` as the last message "so the webview shows error recovery UI (Retry…) instead of a stuck Thinking spinner" (:1943-1965); recoverable errors are logged, not shown (:1910-1913). A turn ending on text is retagged in place to `completion_result` (:1874-1885). An authoritative turn phase (`streaming | completed | awaiting_followup | error | resumable`) is set at turn end (`apps/vscode/src/sdk/sdk-session-event-coordinator.ts:101-125`). Roo: retries show a per-second countdown via `say:api_req_retry_delayed` with `<retry_timer>` (`Task.ts:4268-4329`); a first-chunk failure asks `api_req_failed` with Retry, a mid-stream failure cancels the task (:4217-4245); empty responses get one silent grace retry, then an ask (:3540-3590); request timeout 600s (`src/api/providers/utils/timeout-config.ts:12-16`). Hub status is "reported, never fabricated": each turn owns its running→idle transition (`ARCHITECTURE.md`).

## 6. Model portability

Cline's `@cline/llms` is a gateway: provider manifests registered in `BUILTIN_PROVIDER_REGISTRATIONS` (`providers/gateway.ts:19`), 200+ ids generated from models.dev (`providers/provider-ids.generated.ts`) plus handwritten ones, executed through the Vercel AI SDK (`providers/ai-sdk.ts`). Every model is normalised to one stream: `text-delta`, `reasoning-delta`, `tool-call-delta`, `tool-result`, `usage`, `finish{reason, errorClass, errorRetryable}` (`sdk/packages/shared/src/agent.ts:283-343`). Loop, tools and prompt are shared; per-model: context window / max input (`agentic-compaction.ts:31-48`), capability mapping (`providers/model-capabilities.ts:21-35`), reasoning options (`gateway.ts:74`), error classification (`providers/error-classification.ts`). Switching replaces the API handler mid-task (`apps/vscode/src/sdk/task-proxy.ts:179, 240`). Roo: `buildApiHandler` switch over ~27 providers (`src/api/index.ts:111-178`) behind `ApiHandler { createMessage, getModel, countTokens }` (:91-108); the tool protocol (native vs XML) is chosen per provider/model (`Task.ts:2523-2528`).

## 7. How they know it is good

Cline `evals/README.md`: three layers, contract unit tests (tool-call parsing, thinking preservation), smoke tests (5 scenarios × 3 trials on the CLI), e2e `cline-bench` (12 real bug fixes, Docker); metrics pass@k, pass^k, flakiness; a failure classifier (`evals/analysis/patterns/cline-failures.yaml`). Telemetry anchors `task.completed` on a successful `submit_and_exit` (`ARCHITECTURE.md`) and captures mistake-limit and compaction events (`services/telemetry/core-events.ts`). Roo: no evals package in this clone (`packages/` = build, core, ipc, types, vscode-shim); only `apps/vscode-e2e`. Not found otherwise.

## 8. The feel: what the harness does so a normal model feels smarter than it is

- **Showing the work:** every tool call is a row before it runs (`message-translator.ts:1307-1392`), commands stream output (`agent-runtime.ts:2096-2103`), a checkpoint row with Compare/Restore follows every edit (`checkpoints.mdx`).
- **Never dead-ending:** visible retry countdown (`Task.ts:4320-4329`); the error ask is always the last row so a Retry button exists (`message-translator.ts:1955-1965`); overflow → compact and retry rather than fail (`agent-runtime.ts:1146-1190`; Roo `MAX_CONTEXT_WINDOW_RETRIES`, `Task.ts:4205-4214`); a no-tool answer gets a nudge instead of a hang (`Task.ts:3495-3500`; `agent-runtime.ts:694-702`).
- **One good question:** `ask_question` is told "only ask one question… 2-5 options" (`definitions.ts:819-829`); Roo's `ask_followup_question` requires 2-4 complete, tappable answers that may carry a mode switch (`src/core/prompts/tools/native-tools/ask_followup_question.ts:7-13`) and can auto-pick the first after a timeout (`auto-approval/index.ts:66-83`).
- **Anticipating:** `environment_details` tells the model which files changed since it last read them (`getEnvironmentDetails.ts:165`); the agenda store lets the agent file follow-ups and reminders awaiting approval (`agenda-task-tool.ts:16-33`).
- **Continuity:** `resume_task`/`resume_completed_task` asks (`ExtensionMessage.ts:218-219`); hub sessions attach/detach from any client without stopping the run (`ARCHITECTURE.md` Hub-Backed Runtime 4); checkpoints persist across editor sessions.
- **Judgement-like guardrails:** loop detection and a mistake tracker that inserts a recovery notice into the conversation (`session-runtime-orchestrator.ts:459-464`); tool-repetition ask (`presentAssistantMessage.ts:617-648`).
- **Typing while it works:** Roo queues user messages and drains them at the next ask (`Task.ts:1404-1420`).

## 9. The one thing to copy outright

**Copy:** the ask/say message stream: one `ClineMessage` union where every human touchpoint is a typed `ask` with `ts` identity and `partial` upsert, an auto-approval decision function (`approve | deny | ask | timeout`, `src/core/auto-approval/index.ts:37-45`) in front of each ask, and the rule that a failed request ends with `ask:api_req_failed` as the last row (`message-translator.ts:1943-1965`). It gives Corner steps, questions, approvals and retries as one renderable list without a second protocol.

**Avoid:** Roo's `Task.ask()` resolution mechanics: a 100ms `pWaitFor` poll on instance fields, `lastMessageTs` superseding and `AskIgnoredError` thrown as control flow (`Task.ts:1401-1445`). Cline's own comment calls its checkpoint-cancel dance "hacky" (`src/core/checkpoints/index.ts:281-292`), and Cline replaced this with a callback (`requestToolApproval`) brokered as `approval.requested/resolved` events (`approval-handlers.ts:38-58`), which is what a phone client reconnecting mid-task needs.
