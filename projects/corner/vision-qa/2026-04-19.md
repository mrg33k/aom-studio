## Findings by severity

### 1. EA silence — severity 5 (North Star #1)

**Commitment.** *EA is 100% reliable to talk to. No silence. No dropped messages.*

**Result.** **3/3 messages silent in 60s SLA windows** from the authed dashboard → Elon chat route. Screenshot `02-elon-chat-entered.png` shows Patrik's own message *"hey are you there?"* sent 1h before the run with double-tick seen, no reply. Last genuine Elon message: 7h earlier, *"Foreman pokes only. Marked read silently."* — after that the chat has ten `[accept-R5c-488c6fc0b7a8] [project:corner] project N/10` rows from the R5c acceptance sweep, each marked read with no reply.

**Diagnosis.** `agent_status.slug='elon'` has held `status='working'` since **2026-04-01T17:18:12 UTC** — 439h (18.3 days) stale at QA time. The super-agent tmux is either dead, wedged, or silently dropping pickup; nothing is restarting it. The R5c harness does not exercise this path — `scripts/supabase-listener.py` short-circuits `accept-R5c` sources with synthetic `injected`/`replied` traces (see R5c-real narrative, refactor-plan line 629), so 20/20 PASS is guaranteed even when the real super-agent is dead.

**Why R5c-real green ≠ vision live.** The acceptance test proves the instrumentation plumbing works; the product promise ("you can talk to the EA") requires the super-agent to be alive + routed + replying. Nothing tests that end-to-end today.

**Screenshots.** `02-elon-chat-entered.png`, `03-elon-after-3-messages.png`.

**Fix scope.** Super-agent resurrection watchdog (R10a as drafted); SLA pager on `ea_message_trace` (R10b); and extend R5c harness to hit a non-allowlisted source path so one class of false-positive closes.

### 2. Task success 65% (commitment: 95%) — severity 5 (North Star #4)

**Commitment.** *Tasks hit 95% success rate.*

**Result.** Last 50 tasks: `{done: 30, failed: 16, running: 1, needs_input: 2, cancelled: 1}`. Closed = 46. Success rate = **30/46 = 65.2%**. Gap vs commitment: 29.8 points.

**Breakdown of 16 failures.**

| Bucket | Count | Example error |
|--------|-------|---------------|
| Zombie worker (tmux session exited without finalizing) | **13 (81%)** | `worker tmux session exited without finalizing` |
| Misrouted repo (wrong cwd) | 3 (19%) | `misrouted to aom-studio; R4e-N targets AOM-EA infrastructure` |

The R4e-2 zombie investigation landed `| tee /tmp/task-$id.worker.log` as defense-in-depth and a "brief-order theory" for root cause. The theory did not hold: 13 of the last 16 failures still finalize as zombies. This is the same pattern that caused 3 of today's R5–R8 re-ships to need a fix task. The previous run of this vision-qa task (id `42652646`, 23:03Z) failed the same way.

**Why this matters past the metric.** Zombie workers don't just lower success rate — every zombie consumes the repo lock and leaves the task-runner mid-flight, meaning the next task can't start until cleanup. The North Star "smooth path to success, not a dead end" also fails here: zombie tasks don't auto-retry and the failure reason surfaced to the user (`worker tmux session exited without finalizing`) is not user-actionable.

**Fix scope.** Either finish R4e-2 (root-cause the zombie; stdout capture is now live — analyze logs from the last 13 failures) or build a kill-and-restart supervisor around `scripts/task-runner.sh` that treats any exit-without-finalize as a transient failure and re-queues once. Separate: migrate the three misroute bugs to `scripts/haiku-queue.py` (brief-routing preflight).

**Data.** `findings.json` probe 4.

### 3. Stuck "Working" / typing indicator — severity 5 (live bug #8, pillar 1)

**Commitment.** *Shows when an agent is typing or thinking so the user knows something real is happening.*

**Result.** `agent_status` rows with `status != 'idle'`:

| slug | status | is_super | age | updated_at |
|------|--------|----------|-----|------------|
| **elon** | working | true | **439h (18.3 days)** | 2026-04-01T17:18:12 |
| studio | working | true | 184.7h (7.7 days) | 2026-04-12T07:33:35 |

On the dashboard home view (screenshot `01-home-top.png`) Elon's hero card renders a green `● Working` badge next to it 24/7 and the small three-dot typing animation under the status. Both are derived directly from the persisted `agent_status.status` column (`hooks/useDataPipe.js`). There is no presence/heartbeat channel — the "typing" indicator is just whatever was last written to that column.

**Diagnosis.** The write side (super-agent tmux on boot / on message pickup) sets `status='working'` but nothing clears it. Neither `scripts/relay-respond.py` (reply path) nor `scripts/supabase-listener.py` (inject path) writes `status='idle'` after delivery. When the super-agent dies, the row freezes — no time-to-live, no watchdog sweep. Result: the app is pretending Elon is working on something while he has been unreachable for 18 days.

**Fix scope.** Two writes + one sweep: (a) relay-respond clears status after a successful reply; (b) a periodic sweep resets any `status='working'` row older than 30 min without an active `tasks` row owned by that agent; (c) UI derives typing from a short-lived presence channel (Supabase realtime or a row with expiring timestamp), not from the persisted column.

**Screenshots.** `01-home-top.png`, `02-elon-chat-entered.png` (shows animated dots bottom-left of the chat while Elon is in fact dead).
